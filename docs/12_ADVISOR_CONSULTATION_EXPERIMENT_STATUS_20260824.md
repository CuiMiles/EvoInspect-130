## 1. 项目目标与官方约束

项目目标是构建面向工业组装场景的图像/视频 AOI 系统，在只有 100 张正常样本和 30 张缺陷
样本时完成快速迁移，并检测外观、结构、颜色、缺件、尺寸、逻辑和顺序异常。系统还应支持
操作员反馈、自学习、版本化和回滚。

当前从本地官方材料中确认的约束：

| 项目 | 当前确认内容 |
|---|---|
| 适配数据 | 100 张正常 + 30 张缺陷 |
| 隐藏测试 | 至少 1000 张图片 |
| 目标图像 | 2500×2500 |
| 目标设备 | GTX 2060 或更低 GPU |
| 参考运行时间 | 模型运行时间小于 200 ms，但口径未明确 |
| CPU | 小于 2 s 为挑战目标，具体评分作用未明确 |
| 输入 | 图像和视频 |
| 缺陷范围 | 尺寸、缺件/多件、外观、颜色、逻辑和顺序异常 |
| 交付 | 代码、模型、使用说明、可解释性材料；精确格式仍待澄清 |
| 在线限制 | 离线运行，不依赖远程 API/LLM/大型扩散模型，神经网络主体不超过三个 |

评分材料当前被理解为：竞赛环节占 60%，专家评审占 40%；竞赛部分内部可能按方案完整度
50%、答案准确率 20%、检测时间 30% 计分。但这一层级关系仍需组织方确认。

## 2. 当前 benchmark 的精确定义

### 2.1 数据 benchmark

当前唯一完成完整实验的数据集是 MVTec AD：

- 直接归档共 15 类、5,354 张输入图像；内容哈希重复为 0。
- 原始数据保持只读，划分和派生清单单独保存。
- 已建立“最多 100 normal + 30 seen anomaly”的适配支持协议。
- 支持集、开发集和最终测试集按进程隔离；最终测试标签不进入推理进程。
- 缺陷类型外推切片被保留；某类样本不足时按预先规则缩减支持集。
- 五个 seed 是同一公开图像集合上的确定性不同划分，不能表述为五个独立数据集。

尚未完成的计划数据集包括 DAGM 2007、MVTec LOCO AD、MVTec AD 2；VisA、MPDD、
Real-IAD 等仍是可选项。

### 2.2 当前模型 benchmark

当前正式强基线为 Amazon Science 上游 PatchCore：

- 仓库：`amazon-science/patchcore-inspection`
- 固定 commit：`fcaa92f124fb1ad74a7acf56726decd4b27cbcad`
- 许可证：Apache-2.0，LICENSE/NOTICE 已保留
- 上游 checkout：未修改

## 4. 创新实验的具体结论

### 4.1 HeteroMemory v1/v2

最初设想是把 30 个已知缺陷视为从正常流形指向不同异常分布的方向，并与正常 PatchCore
记忆结合。v1 直接产生总体和 unseen 退化；v2 虽然总体 F1 略升，但 unseen F1 和 AUROC
下降。这说明当前缺陷方向建模会过拟合少量 seen anomalies，不能宣称提升未知缺陷泛化。

### 4.2 GuardedFusion v1/v2-safe

该路线融合 PatchCore-lite 正常记忆距离和支持缺陷训练的线性头，并加入开发集门控和确定性
回退。v2-safe 相对 PatchCore-lite 的整体 F1 从 0.8534 提高到 0.8705，unseen F1 从
0.8131 提高到 0.8227，是一个真实的受控正结果。

但是，固定正式上游 PatchCore 在相同类别、seed 和划分下达到 F1 0.9224，比 v2-safe 高
0.0518；AUROC 也高 0.0443。配对任务 bootstrap 的 F1 差值 95% CI 为
[0.0288, 0.0770]。因此 v2-safe 只能作为“改进弱基线、但被强基线否定”的研究过程，
不能作为最终创新。

### 4.3 GuardedFusion v3

v3 使用固定上游 PatchCore embedding 的全局均值和 top-32 残差描述符训练监督头，只允许
在 PatchCore 证据边界内救援负样本。15 类 × 3 开发 seeds 共 45 次：44 次回退，唯一启用
的 carpet seed 132 使 F1 下降 0.0375。最终 ΔF1 -0.0008，unseen ΔF1 -0.0016，
0/44/1 胜/平/负，已淘汰。

### 4.4 MaskedPrototype v4

v4 利用支持缺陷 mask 在 PatchCore 特征网格上选取局部缺陷原型，最多保存 2,048 个原型，
只作为受保护的救援分数。45 个开发任务全部拒绝救援并精确回退到 PatchCore。所有主指标
变化为 0。精确回退说明安全机制有效，但不是创新收益，已淘汰。

### 4.5 Layer2/尺度实验

早期 layer2 路线希望利用浅层高分辨率特征改善小缺陷，但 8 类开发实验平均 F1 下降
0.0616，且开发集在 cable、pill 等类别选择的尺度方向与测试结果相反。该结果只淘汰了
“简单替换层或用小开发集选择层”的方案，不等于否定所有高分辨率局部复检。

## 7. 距离最终算法结果还缺什么

### 7.1 必须完成的算法闭环

1. 选择并冻结一个清晰、可解释且与最近工作有精确差异的主创新。
2. 在 seeds 130--132 开发，不使用 seeds 133--137 或 138--142 的测试标签选模型。
3. 在全 15 类进行至少三 seed 配对实验和受控消融。
4. 相对固定上游 PatchCore证明稳定收益或明确的质量-时延 Pareto 改善。
5. 在开发阶段通过预先写定的保留门槛后冻结代码和配置。
6. 只在此后解封 seeds 138--142，完成 15 类 × 5 seeds 的独立确认。
7. 报告总体/seen/unseen、图像/像素/区域、低 FPR、置信区间和失败类别。
8. 如果确认失败，必须诚实淘汰，不能回到确认结果调参数。

### 7.2 强基线覆盖缺口

当前只完成正式 PatchCore。仍计划至少补充：

- EfficientAD：实时轻量强基线；
- AnomalyDINO：基础模型特征/记忆强基线；
- AHL 或 DRA：少量监督、开放集路线；
- RealNet 或 GLASS：合成/判别式异常定位路线；
- 简单增量记忆：持续学习对照。

需要导师决定最低必须完成几类，避免基线过少影响论文可信度，也避免基线过多挤占主创新时间。

### 7.3 外部有效性缺口

- 只有 MVTec AD；尚无第二独立公开数据集。
- 没有组装逻辑异常专用数据验证。
- 没有照明、相机、时间漂移切片。
- 没有真正的高分辨率小缺陷协议。
- 没有内部隐藏模拟。

### 7.4 部署证据缺口

- 没有 2500×2500 端到端测试。
- 没有 GTX 2060 或更低设备实测。
- 没有 CPU 端到端测试。
- 当前 224×224 RTX 3090 时延只覆盖模型段。
- 没有预处理、后处理、序列化和 I/O 的完整 p50/p95/最大值。
- 没有 TensorRT/ONNX/量化、功耗、显存上限和压力测试。

### 7.5 系统与提交缺口

- 视频事件和逻辑/顺序异常尚未实现。
- 操作员反馈流、回放、正则/蒸馏、影子测试、发布门禁和回滚尚未实测。
- 已知/未知标签、置信度校准、组件/工序解释和最近正常证据没有完整集成。
- 尚未形成离线部署包、稳定接口、演示 UI、模型使用说明和最终可解释性文档。
- 根仓库 Git commit 不可用，实验记录只能写 `UNAVAILABLE`，源码 provenance 不完整。
- MVTec 数据用途、预训练权重分发和直接归档来源仍需人工签核。

## 8. 建议的下一主创新草案：BudgetRouter 局部高分辨率复检

以下只是供导师评审的草案，尚未冻结，导师回复前不运行。

### 8.1 草案结构

1. 用固定 PatchCore/轻量学生对整图进行低分辨率全局筛查。
2. 根据异常图、局部不确定性、组件位置和计算预算选择少量 ROI，而不是对整张 2500×2500
   图像始终高分辨率推理。
3. 对选中 ROI 用共享 backbone 的高分辨率局部特征或轻量局部细化器重新评分。
4. 将全局与局部 anomaly map 在开发集冻结的规则下融合。
5. 路由器显式记录选中区域、复检原因、额外时延和总预算。
6. 如果局部细化不能可靠改善，确定性回退到原 PatchCore 输出。

潜在创新价值是同时针对小缺陷、低 FPR 和 2500×2500 时延预算，而不是简单增加模型数量。
需要通过最近工作检索确定它与已有 coarse-to-fine AOI、PatchCore 多尺度和动态推理方法的精确
差异，尚不能使用“首创”等词。

### 8.2 建议消融

| 编号 | 方案 | 目的 |
|---|---|---|
| B0 | 固定上游 PatchCore | 正式强基线 |
| B1 | 整图始终高分辨率 | 高成本质量上限 |
| A1 | 只有局部高分辨率评分，无动态路由 | 验证局部细化本身 |
| A2 | A1 + 动态 ROI 路由 | 验证路由选择 |
| A3 | A2 + 组件/位置先验 | 验证结构信息 |
| A4 | A3 + 硬时延预算/提前退出 | 验证 BudgetRouter 完整贡献 |
| A5 | A4 去除安全回退 | 验证回退的质量与风险代价 |

### 8.3 建议开发顺序

1. CPU 单测和合成 fixture，验证 ROI、坐标、融合和预算逻辑。
2. wood/capsule/transistor × seed 130 做单 seed smoke。
3. 若功能正确，再运行三类 × seeds 130--132 的最小消融。
4. 只有预注册门槛通过，才扩展 15 类 × 3 开发 seeds。
5. 冻结方案后才运行 seeds 138--142。
